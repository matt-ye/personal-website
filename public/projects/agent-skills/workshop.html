應用場景決策表

網頁擷取：defuddle vs crawl4ai（有實測數據）

同一個維基百科長文，兩個工具的實測結果：

工具輸出字元殘留導覽雜訊
crawl4ai 原始輸出214,225整片側欄、選單都在
crawl4ai 內容過濾後150,277仍有導覽，且砍掉了真正的正文
defuddle164,909零

但換成 JS 渲染的頁面，結果完全反轉：

工具抓到的內容
defuddle88 字元 ＝ 失效
crawl4ai1,666 字元，目標內容全數取得

決策規則：預設用 defuddle（更乾淨、零基建）。只有當 defuddle 回傳異常短的內容時，才換 crawl4ai。

⚠ 特別記住：defuddle 對 JS 頁面是「靜默失效」——不報錯，只回傳近乎空白。這比報錯危險，因為你可能不知道自己漏了東西。

怎麼評估一個 Skill（可複用 SOP）

這節是這份文件的核心。清單會過期，方法不會。

  1. 先判定它是什麼——不要預設別人給的 GitHub 連結是 agent skill。它可能是獨立應用、MCP server、SaaS 開源版，甚至是反過來呼叫 Claude 的平台。先定類別，才不會用錯誤的判準去評
  2. 回原始 repo，不看目錄站——實際遇過目錄站標示的星數與 GitHub API 實測差到 600 倍
  3. 讀 LICENSE 檔本身，不要讀 README 對授權的描述。真實案例：README 說「建議標註出處」，LICENSE 檔寫的是強制歸屬條款
  4. 逐一列出 hooks——hooks 會改變每一回合的行為，是最該審的部分。要問：掛在哪個事件？做什麼？影響單一專案還是全域？能不能關？
  5. 查資料流——哪些功能純本地、哪些會送資料出去？能否指定本機模型？有敏感資料的人，這條是紅線不是偏好
  6. 查維護訊號——最後 commit、issue 回應速度、有沒有懸而未決的資安揭露。star 數高不等於安全，反而放大風險半徑
  7. 安裝路徑要挑——同一個 skill 常有多種裝法。優先選能乾淨移除的（如官方 plugin 機制），避開會直接改寫全域設定檔的自家安裝器
  8. 小規模試點再收編——拋棄式環境、少量樣本、危險功能不啟用。實測往往推翻紙上評估（〈應用場景決策表〉的 defuddle vs crawl4ai 就是例子）
本清單的判定基於 2026 年 8 月的查證。工具生態變動快，採用前請重新確認維護狀態與授權——特別是標為 E（評估中）的項目，判定可能因上游修復而改變。
