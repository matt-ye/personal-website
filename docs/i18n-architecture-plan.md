# 中英雙語架構重構規劃

**狀態：** ✅ 已實作完成（2026-08-18：全站遷入 `[...lang]`，課程 26 週英文版全部上線，94 → 119 頁）。
本文件保留為決策紀錄——「為什麼這樣做」看這裡；「現在怎麼做一頁」看根目錄
`CLAUDE.md` 的雙語一節與 `curriculum/README.md` 的部署慣例。
**撰寫日期：** 2026-08-07
**目的：** 讓英文內容有獨立網址、能被單獨索引與分享。這份文件先把現況、選項與代價講清楚，供評估後再決定要不要做、以及做到什麼程度。

---

## 1. 現在的機制與它的三個問題

目前每個頁面只有一個網址，中英文**同時**存在於 HTML 裡，由 `<T zh en>` 產出兩組 `<span>`，再靠 CSS（`<html data-lang>`）顯示其中一組。語言切換是純前端的 class 切換，不改變網址。

這造成三件事：

1. **英文內容無法被單獨索引。** 搜尋引擎看到的是「一個網址裡混著中英文」。它得自己猜這頁的主要語言，猜錯就不會出現在英文搜尋結果。
2. **沒辦法分享英文版。** 把 `mattye.dev/coaching` 傳給國際評審，對方打開會先看到中文，得自己找到右上角的切換鈕。多數人不會找。
3. **爬蟲讀到混雜字串。** 不執行 CSS 的爬蟲（含多數 LLM）看到的是 `首頁Home演講Speeches` 這種相連文字。

> 2026-07 已做過緩解：`<T>` 的兩個 span 各自加上 `lang` 屬性，非預設語言加 `hidden`，並由 `Header` 的 `syncLangHidden()` 在切換時對調。那讓爬蟲**有機會**正確分辨，但不是根治——網址層級的問題只能用網址解決。

>
> 一個 `.astro` 檔產不出兩個網址。已採用 **`[...lang]/xxx.astro` 動態路由**，

> `speeches` 753 → `index` 645，合計含 1,274 行 client script）照同一模式逐頁搬。

## 3. 一個會改變決策的事實

**架構改完，得到的是「英文網址」，不是「英文網站」。**

- UI 文字（365 個 `<T>`）已經雙語 ✓
- Sheet 的 `_eng` 欄位只填了一部分，缺的會退回中文
- 文章 11 篇只有 1 篇有英文版 → `/en/writing` 會列出 10 篇中文標題的文章

**路由是這件事裡簡單的部分；內容翻譯才是瓶頸，而且無法自動化。** 若先把架構做完才發現沒有英文內容可放，等於做了一半白工，還多背一套要維護的路由。

因此下面的方案排序，是按「投入 ÷ 實際效益」而不是「完整度」。

## 4. 三個方案

### 方案 A：全站鏡像

13 個 Astro 頁 + 38 個靜態頁都做成雙語，每頁兩個網址。

- **優點：** 最完整，所有內容都能被單獨索引與分享。
- **代價：** 38 個手寫靜態頁要變成 76 個。而且那些頁的 metadata（favicon、OG、JSON-LD）目前是**手工維護**的——2026-07 補齊時是用腳本批次寫入 38 個檔案。鏡像後這筆債翻倍：每次新增一個 meta 標籤要改 76 處。
- **適合時機：** 英文是主要受眾之一，且願意投入翻譯全部內容。

### 方案 B：只做 Astro 的 13 頁（靜態 38 頁維持現狀）

真正需要被正確索引、需要分享給國際觀眾的是首頁、`coaching`、`speeches`、`projects`、`writing`。38 個靜態頁是長篇筆記，中文為主，維持單一網址與現有的 CSS 切換。

- **優點：** 涵蓋 90% 的實際分享場景，工作量約為 A 的三分之一。
- **代價：** 站內會有兩種語言機制並存（Astro 頁走網址、靜態頁走 CSS），需在文件中寫清楚，否則之後容易誤改。
- **適合時機：** 希望英文內容進 Google，且核心頁面的英文內容已經齊備。

### 方案 C：只做一頁英文（推薦作為第一步）

在 `/en/` 放一頁英文的「自我介紹 + 經歷 + 作品索引」，專門給國際觀眾（例如 Falling Walls 評審、國際合作對象）。**不動路由架構、不碰 `<T>` 機制。**

- **優點：** 成本約為方案 B 的十分之一。若實際需求是「把一個網址給外國人看」，這就解決了。
- **代價：** 英文內容不會進到各分頁的搜尋結果，只有這一頁。
- **適合時機：** 還不確定英文流量是否真的存在。

### 建議順序

先做 **C**，觀察一至兩個月的實際使用（GA4 可看 `/en/` 的流量與來源），再決定是否升級到 **B**。

理由：C 的產出可以完整併入 B（那一頁會成為 `/en/` 的首頁），不是白做；而 B 一旦開工，會牽動路由、建置、內部連結與 analytics，中途反悔的成本很高。

## 5. 方案 B 的執行流程

若評估後選 B，建議按此順序。每個 Phase 都能獨立驗證、獨立上線，不必一次做完。

### Phase 0 — 決策
確認第 7 節的四個問題。這些答案會影響後續每一個 Phase 的做法，先定案再開工。

### Phase 1 — 基礎設施（不動任何內容）

- `astro.config.mjs` 啟用 Astro 6 原生 i18n：
  - `defaultLocale: 'zh-TW'`、`locales: ['zh-TW', 'en']`
  - **預設語言不加前綴**（`prefixDefaultLocale: false`）→ 現有網址完全不變，既有 SEO 與外部連結不受影響
- `BaseLayout` 依 locale 產出：`<html lang>`、`og:locale`、`og:locale:alternate`、以及**互指的 `hreflang`**
- sitemap 輸出兩個語言，並帶 hreflang 對應
- 語言切換鈕從「切 CSS class」改為「換網址」（保留當前路徑，`/coaching` ↔ `/en/coaching`）

**驗證：** 兩個語言的頁面都能建置；`hreflang` 互指正確；現有中文網址無一改變。

### Phase 2 — 搬移內容已經雙語的頁面

刻意從「介面文字多、內文少」的頁面開始，因為這些頁的文字幾乎都在 `<T>` 與 Sheet 裡，已經是雙語，搬移風險最低：

1. `sponsor` — 最單純，當試點
2. `index`
3. `coaching`、`speeches` — Sheet 驅動，要處理 `_eng` 缺值
4. `projects/index`

**驗證：** 每頁的兩個語言版本內容正確、`hreflang` 成對、切換鈕跳對網址。

### Phase 3 — 文章（最花時間）

- content schema 增加 `lang` 與 `translationOf`，讓中英版本互相認得（現有的 `titleEn` 是單檔雙語，方案 B 下應改為「兩個檔案互指」）
- **只翻值得翻的**，不是全部 11 篇
- 沒有英文版的文章，`/en/writing` **不列出**它——列出來卻是中文，比不列更糟

### Phase 4 — 收尾

- 移除 `<T>` 的雙 DOM 機制。此時每頁只有一種語言，`<T>` 不再需要——**這會根治第 1 節的第 3 個問題**（爬蟲讀到混雜語言），而不只是緩解
- `llms.txt`、README、社群連結指向正確的語言版本

## 6. 已知的坑

這些是現在就該知道的，不是做到一半才發現的：

1. **`localStorage` 的語言偏好與網址會衝突。** 使用者上次選英文，但點進中文網址時誰贏？建議**網址永遠優先**，`localStorage` 僅在使用者從未指定語言時決定是否導向。
2. **Sheet 的 `_eng` 欄位不完整。** 英文頁會出現中文內容。需決定策略：退回中文（建議，並加 `lang="zh-TW"` 標註）或整段隱藏。空白比中文更糟。
3. **`diet-calculator` 是重災區。** 大量字串寫在 JS 裡用 `L()` 包，locale 化要逐一處理，是單一檔案裡最大的工作量。
4. **`Tour.astro` 的 10 步導覽文案**同樣在 JS 裡，要一起 locale 化。
5. **GA4 會出現斷層。** 頁面路徑多了 `/en/`，現有報表的 path 比對會失準。需先決定語言維度怎麼記（建議在 `BaseLayout` 送出 locale 當 custom dimension）。
6. **38 個靜態頁的 metadata 債。** 若採方案 B 不搬它們，這筆手工維護的債會留著：每次新增 meta 標籤仍要批次改 38 處。這是獨立的技術債，值得單獨排一次「靜態頁遷移成 Astro 頁」的計畫。
7. **`sponsor` 的金流不受影響**，但 `/en/sponsor` 的感謝頁仍會落在 `telaaurealab.com`（worker 端 return URL 為白名單設計），這點在英文頁上更需要寫清楚。
